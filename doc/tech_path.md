# 技术选型

## 准备工作
下面列举的这些内容其实从最开始并没有考虑那么齐全。如果选出最重要的内容，建议是用户画像和用户功能呈现的考虑，他们决定了软件产品的设计方向和底色。

### 产品界面
产品界面考虑
- 用户画像，最终用户是谁？用户更偏向怎样的操作？
- 产品最终想要呈现什么功能、内容给最终客户？

#### 用户画像
一线支持
- 快速开通业务。操作要求快速、安全、简洁。很多现场工程师喜欢CLI一键开通
- 简单的参数设定，大部分参数保持默认，甚至隐藏。但需要看到各种参数的呈现（习惯？真实需要？客户需求？）

客户
- 有些客户懂业务逻辑，有些客户了解业务需求，但不能要求用户是全才。所以客户的要求是清楚操作的目的是什么，但不要求是业务专家
  - 运维部门
  - 数据分析部门
- 使用NBI的客户了解熟悉业务

#### 用户功能
从自己使用各种软件的习惯来看，好的软件有这些特点
- 操作简单且丝滑，复杂的操作都有非常简单易于上手的操作逻辑
- 提供复杂的参数配置让专家能够进行功能微调，但即便是专家功能，也需要让专家是思路聚焦在参数上，而不要花时间考虑软件的操作逻辑
- 总结：
  - 像游戏一样的UI呈现，丝滑的手感，所见即所得，操作的结果都是可预期的。
  - 幂等操作避免复杂的操作逻辑

### 管理对象
#### 对象类型
- 节点
  - 设备、子架、板卡、端口等各种物理资源
  - HOST、VM、裸金属
  - 云化容器、编排器
  - 各种外部依赖服务
- 连接
  - 节点之间的连接关系，可以是P2P，P2MP，以及网络
  - 路由

#### 生命周期
- 基本原则是点决定线的生命周期，不存在没有点的连接关系
- 每个节点和连接具有自己独立的生命周期，但不会超脱父对象而纯在。例如连接可以单独被创建和删除，但当相关节点被删除的时候，连接也会被删除掉
- 有些节点的生命周期通过状态机决定，只有特定状态下才能被删除

### 数据规模/压力预估
数据规模决定DB的选型，也是软件架构方面的重要参考。所有逻辑中，最重要的就是数据落盘，网管和设备的数据实时保持一致才能保证后续所有操作是可靠的。

#### 普通业务数据
普通业务数据通常指配置数据、告警、性能等等。例如目标是管理1万个设备，根据设备形态和组网情况，可以大致估算各种数据的量级。
当然还有一些通用的数据，例如日志、报告、服务状态等等，这些数据也会随着网络规模的扩大而需要更多的资源。

#### 海量大数据
海量数据处理主要来自三个方面
- 配置数据同步：当网元达到一定数量的收，每次进行全网数据同步就需要处理大量数据。数据同步不仅仅需要考虑数据落盘，还有实时数据/状态计算，相关对象更新等等。配置数据同步会对CPU，MEM，磁盘IO都带来冲击。
- 告警风暴：告警处理和配置类似，除了落盘，也涉及复杂的状态计算和更新，当产生告警风暴的时候，会瞬时推高系统负载，而且告警风暴不可预知，只能系统留出余量能够应对告警风暴，同时程序逻辑也需要平滑告警风暴，抑制告警风暴。
- 性能数据：最难啃的大头就是性能数据，特别是需要应对秒级Telemetry的时候，如何平滑系统负载，如何充分利用DB的落盘能力，如何根据不同的硬件环境调优参数，将是最难的挑战。

海量大数据的量级需要提前根据计划的网络规模进行估算，后期进行压力测试和性能调优还要按这个估算进行验证。

### 并发访问
当电信网管部署在各个局部网络中进行专网管理的时候，并发访问要求并不高。但当进行几种部署，通过分权分域的管控，让各个地市、部门访问集中网管的时候，并发访问的问题就凸显出来。移动OMC通用技术规范可以是一个很好的参考，例如并发用户数>=500。

### 数据/服务安全
- HA，7x24小时服务
- 灾备

## 技术选型
技术选型在于产品本身需要提供什么功能和服务。理论上，市面上的绝大部分产品都能满足需求，但100%满足需求的产品应该是很难找到。底层逻辑是找到自己最需要的功能，看看选择的产品、框架、技术是否满足需求，然后找一个自己觉得最简单，或最舒服的产品上手试试。如果本身对某些产品就非常熟悉，非常清楚这个产品的优缺点，那么选择的方式又有差异。

> 很多时候，用自己熟悉的产品或实现逻辑，会是一个比较好的选择。但建议可以适当的尝试新技术，保持产品的活力

### 前端

#### 框架
Angular非常熟悉了，React也快速入了个门，如果按目前的经验来选择，我可能会选择React。Vue没有经验。这里不做完整的对比评测，网上很多文章。
- Angular
  - 在大型软件的优势非常明显，HTML/CSS/TS完整分割，逻辑非常清晰。基于component的方式有很好的对象封装体验。但缺点也非常明显
      - 后端开发人员，例如Java开发学习Angular会非常快上手，但前端的js开发同学要转向对象方式的封装，要走的路很长。生成component的代码容易，但面向对象的设计思路不太容易转换
      - Angular的component会增加中间dom节点，导致dom树不是那么干净，特别是需要对组件库进行css控制的时候会比较别扭
      - form的处理看起很干净完美，但实现逻辑稍微有点复杂。如果不清楚其底层逻辑会导致调试很麻烦
- React（仅仅学习时尝试过，未真正实战）
  - 极其容易上手，而且代码逻辑更简单，学习曲线远远小于Angular。还没有大规模使用过，最满意的是dom节点干净，代码实现清晰简单。
  - 仅仅从经验上分析
    - 从面向对象的角度，只有较为简单的封装。大项目的维护难度可能会比Angular麻烦。通过typescript是否会扭转这一局面？（待定）

为什么更推荐react？
- 上手难度低，可以快速出模型
- 通过提前规划组件来降低海量组件的复杂度
- 国内有时候访问angular官方网站比较慢

#### 组件库

ant-design
- 功能全且强大, 碾压其他大部分组件库
- react原生（未用过react的版本）
- angular版本的实现不是那么统一，较多硬编码，导致调整样式比较麻烦
- 尝试过的几个组件库中，颜值算最低的

material
- angular原生组件库，和angular完美契合
- 组件功能较ant-design少，需要自行扩充一些功能


heroui / tailwindcss
- 学习react都时候发现系列组件库，很多都是一眼相中，颜值相当在线。暂时推荐heroui + tailwindcss
- 大部分库的组件功能和material差不多

还有很多组件库可以选择，总体来说功能大同小异，大部分选择都不会错。经过多番折腾，个人还是更喜欢轻量级的封装，提供更多定制化的可能的组件库，当然颜值排第一位。

#### 拓扑图组件

vis.js
- 开源神器，简单，易用且效率很高。
- 颜值一般，功能较单一

d3.js
- 功能强大，几乎能满足所有功能
- 数据驱动的方式在某些处理逻辑上比较麻烦，甚至带来难度。例如节点上引入一组图标

svg
- 如何只是支持拓扑图，以及一些专有的图像展示，基于svg进行自定义开发类似vis.js的功能，工作量不算大，所以也算一个选项。好处是完全可控，任何功能均可自行定义扩展
- 需要自行补充功能，例如各种layout算法需要自行开发，或引入d3帮忙控制


### 后端

#### 开发语言
选择团队熟悉的语言，除非想尝鲜。

常规选项：Java为主，python/shell脚本辅助集成
- 如果为了追求极致，Rust也可以是一个选项


几点思考
Java
- 目前服务器的内存已经足够大，但本着充分利用资源的原则，一个服务真正需要动则几百M的内存开销吗？Java在大型服务集群中，每个服务对内存的消耗，加总后非常可观。Rust能带来多大的提升？
- Springboot如日中天，但真的必须吗？
  - 开箱即用，同时意味着框架的厚重和复杂度
  - 完全可控的代码架构是否可以秒杀springboot带来的优势？

Python
- 随着向AN的方向发展，python的地位会越来越高，如何协调python和主语言之间的协同？消息中心？
- 数据分析、集成工具之外，python是否还有其他应用场景？

### 数据库
所有技术选型中最大的坑，一旦选错，只有重来。
产品启动阶段，可能并没有考虑那么全面，但从产品后续的发展来看，数据库选型需要考虑
- HA：优选集群
- 灾备：部分开源DB支持灾备
- 查询方式：影响查询逻辑的实现。数据库操作中，最麻烦的就是各种查询，需要保持简单及高效

如果需要处理海量数据，还需考虑
- 压缩比
- 存储方式（行存储/列存储）
- 入库性能


一些注意事项
- 文档数据库的自由度会让关系数据库黯然失色，但复杂的汇聚逻辑又完败于关系数据库
- ZZKK几乎都是无缝对接MySQL、PostgreDB的产品，如果有计划ZZKK的产品，建议PostgreDB
- MongoDB在很多时候确实非常优秀，甚至在大数据处理上，代码逻辑分表的入库性能有机会赶超MongoDB自己的时序库。其他数据库是否也有这种情况？
- 产品需要多种不同数据库支持的时候需要慎重，复杂度超乎想象。例如log入ES，配置、告警等入MongoDB/PostgredB，性能数据入时序库。每一种处理都提供呢极致服务的同时，维护的灾难也在慢慢到来。当然，数据量大到只能这么选择的时候是例外。
